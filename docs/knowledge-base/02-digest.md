# 02. 주제 정보 만들기

주제 정보(digest)는 시민이 이 소식에 대해 **사실로 알고 있는 것**입니다. 프롬프트의 `[알고 있는 것]` 칸으로 들어가고, 시민은 여기 있는 것만 사실로 말하도록 지시받습니다.

## 형식

```json
{
  "summary": "이 소식이 무엇인지 두 문장",
  "facts": [
    {"statement": "다음 달 1일부터 공영주차장 3곳이 밤 10시~오전 7시에도 요금을 받는다",
     "condition": "", "status": "확정·시행"},
    {"statement": "인근 주민은 월 3만 원 야간 정기권을 살 수 있다",
     "condition": "주소지가 해당 동인 주민", "status": "확정·시행"}
  ]
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `summary` | 예 | 소식 전체를 두 문장 안으로. 첫 메시지와 카드 판정에도 쓰입니다 |
| `facts[].statement` | 예 | 사실 한 줄. 시기와 대상을 문장 안에 넣습니다 |
| `facts[].condition` | 아니요 | 누구에게만 해당하는지(희망자, 저소득층, 특정 지역 등) |
| `facts[].status` | 예 | 아래 네 가지 중 하나 |
| `not_stated` | 아니요 | 원문에 없는 것. **비워 두기를 권장합니다**(아래 참고) |

### status 값

status는 그 사실이 **얼마나 확실한지**를 나타냅니다. sarangbang은 이 값을 사실 뒤에 `[확정·시행]`처럼 붙여 보여 주기만 하므로, 도메인에 맞는 어휘를 써도 됩니다. 어휘는 `meta.json`의 `statuses`에 적고, 없으면 기본 어휘를 씁니다.

```json
"statuses": ["공식 발표", "출시 예정", "유출·루머", "이전 모델"]
```

| 기본 어휘 | 쓰는 경우 | 신제품 출시 예 | 미디어 예 |
|---|---|---|---|
| `확정·시행` | 이미 결정됐거나 시행 중 | 공식 발표 | 공식 확인 |
| `계획·목표` | 하겠다고 밝혔지만 아직 전 | 출시 예정 | 방영 예정 |
| `과거 실적` | 이전에 있었던 일, 지난 통계 | 이전 모델 | 지난 시즌 |
| `검토` | 검토·논의 단계 | 유출·루머 | 보도·루머 |

어떤 어휘를 쓰든 **확인된 것과 확인되지 않은 것을 구분**하는 것이 핵심입니다. 섞이면 시민이 "이미 정해졌다"와 "아직 모른다"를 뒤바꿔 말합니다. 상태는 반드시 원문에서 확인합니다. 소문이나 유출 정보는 주제 정보 대신 쟁점 카드의 `premises`(들은 얘기)로 넣는 방법도 있습니다. 그러면 시민에게 추측·의문형으로만 꺼내라는 안내가 함께 붙습니다.

## 사실 고르는 기준

1. **읽는 사람에게 무엇이 달라지거나 새로 알려졌는지에 답하는 사실만** 고릅니다. 추진 배경, 작성 기관의 절차, 홍보 문구("업계 최초", "역대급")는 뺍니다.
2. **시기와 대상을 문장 안에** 넣습니다. "요금을 받는다"가 아니라 "다음 달 1일부터 3곳에서 밤 10시~오전 7시에 요금을 받는다"로 씁니다.
3. **수치는 원문과 대조**합니다. LLM으로 뽑으면 큰 수치 중 일부만 옮기거나 단위를 바꾸는 경우가 있습니다.
4. **8~12개**를 기준으로 합니다. 너무 적으면 시민이 사실을 지어내고, 너무 많으면 앞의 몇 개만 반복합니다. 소식의 대상이 아닌 시민(`personas.json`에서 `affected: false`)에게는 앞의 4개만 보입니다(사양의 `known_trim`). 그래서 중요한 사실을 앞에 둡니다.

### 좋은 예와 나쁜 예

| 나쁜 예 | 문제 | 고친 예 |
|---|---|---|
| 주차 질서 확립을 위해 야간 유료화를 추진한다 | 목적 서술이라 시민에게 달라지는 것이 없음 | 다음 달 1일부터 공영주차장 3곳이 밤 10시~오전 7시에도 시간당 500원을 받는다 |
| 정기권을 도입한다 | 누가, 얼마에, 언제부터가 없음 | 해당 동 주민은 다음 달부터 월 3만 원 야간 정기권을 살 수 있다 |
| 요금 수입은 주차 환경 개선에 쓸 예정이며 이미 확정됐다 | 계획과 확정이 섞임 | (status: 계획·목표) 요금 수입은 주차장 조명·CCTV 개선에 쓸 계획이다 |

## '원문에 없는 것'을 넣지 않는 이유

`not_stated`에 "배터리 용량은?", "총비용은 얼마인가?" 같은 미정 사항을 넣었을 때, 시민들이 "그런 얘기는 없던데"라는 말을 되풀이하고 대화가 그쪽으로 쏠린 경우가 있었습니다(EXAONE·A.X 실측). 미정 사항은 쟁점 카드의 `ask_form`(시민이 던질 질문)으로 넣는 편이 자연스럽습니다.

## LLM으로 뽑기

```bash
cd examples
python -m kb_tools.extract_digest 원문.txt -o knowledge-bases/my-topic/digest.json --title "공영주차장 야간 유료화"
```

도메인 상태 어휘를 쓰려면 `--statuses "공식 발표,출시 예정,유출·루머,이전 모델"`처럼 `meta.json`의 `statuses`와 같은 값을 줍니다.

[`examples/kb_tools/extract_digest.py`](../../examples/kb_tools/extract_digest.py)는 원문을 한 번에 넘기고 위 기준을 지시해 JSON으로 받습니다. 원문이 길면(대략 2만 자 이상) 장 단위로 나눠 뽑은 뒤 합치는 편이 안정적입니다. 뽑은 결과는 반드시 사람이 다음을 점검합니다.

- [ ] 모든 수치가 원문과 같은가
- [ ] status가 원문 표현과 맞는가(확정인지, 예정인지, 소문인지)
- [ ] 시민에게 달라지는 것이 없는 사실을 뺐는가
- [ ] condition에 일부 사람이 아닌 내용(장소, 시간, '이용자' 같은 전체)이 들어가지 않았는가
- [ ] 원문에 없는 날짜·기간을 계산해 넣지 않았는가
- [ ] 중요한 사실이 앞쪽 4개 안에 있는가
